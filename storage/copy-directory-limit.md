# COPY 小批写入后目录文件数达到上限

**暂时缓解**

一张以追加为主的表每五分钟写入约七万行，每两千行提交。约三天后目录项达到上限，手工执行 `COMPACT TABLE` 后写入暂时恢复。现场反馈平时没有扫描这张表。

## 三种 COPY 入口

下面是示例语句，`t` 代表测试表。记录核对的是磐维 OLAP 2.4.6 参考版本中支持相应维护功能的表。现场称其为 ORC 表，仍需用实际表定义、写入语句及构建版本确认适用范围。

| 写入方式 | 会生成 INSERT 形式的计划吗 | 写入本身的自动维护行为 |
| --- | --- | --- |
| `COPY t FROM STDIN WITH (FORMAT csv)` | 不会 | 没有普通 INSERT 的自动归档检查，也不直接请求 Compact。客户端从本地 CSV 读数据再发给服务端属于这一行。 |
| `COPY t FROM '/import/a.csv' WITH (FORMAT csv)` | 不会 | 这是服务端本地文件，走 COPY 写入路径，同样没有上述检查。 |
| `COPY t FROM 'hdfs://…/a.csv' WITH (FORMAT csv)` | 会，目标表和远端输入须受该版本支持 | 专门的装载路径生成写入计划并直接执行，仍跳过普通 INSERT 的自动归档检查，也不直接请求 Compact。 |
| 普通 `INSERT INTO t …` | 本身就是 INSERT | 对支持归档的目标表，在启用相关设置、达到触发条件时可提交 Archive 请求。 |

CSV 指定输入格式。客户端把 CSV 通过连接发送时，服务端执行的是 `COPY FROM STDIN`。在核对的版本中，这三种 COPY 入口本身也不直接提交 Clean 请求。同一张表仍可能由其他维护任务触发清理。

## 文件何时会减少

- **Archive** 归档旧提交记录，缩短活跃时间线。打开自动归档后仍要有检查机会、满足条件，才会产生后台请求。
- **Compact** 将可合并的小文件或增量数据写成新文件，记录旧文件已被替换。查询需要读取的文件可以变少，重写过程中磁盘目录内的新旧文件可能同时存在。
- **Clean** 按保留策略回收符合条件的旧文件。归档或合并结束后可以按条件派发后续任务。后台任务可能尚未运行，也可能已经运行而旧文件还在保留期内。

对支持这一机制的表，查询计划实际需要枚举目标表文件时，也有机会检查归档或合并条件。只写不扫会少一次检查机会。`SELECT … LIMIT 0` 如果被优化成空结果，就不会走这条路径。旧文件的替换记录由合并等重写操作产生，缺少扫描不能单独证明 Clean 停止工作。

## 怎样判断这次卡在哪一步

1. 核对失败的是数据目录、分区目录还是提交时间线目录，按同一目录的**直接子项**计数。把写入前后新增的数据文件、辅助文件、提交记录分别计数。按给出的行数折算，每五分钟约 35 次提交，一次提交可能有多个并行写入者，提交数不能当作文件数。[HDFS 目录项限制](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/hdfs-default.xml)
2. 在同一张表、同一时间窗对齐维护请求的来源、开始和结束时间、合并结果、替换记录以及 Clean 的删除数量。没有合并候选、已有替换记录但尚在保留期、清理失败，是三种不同的处置方向。单凭手工合并后能写入，无法判定此前是 Clean 未触发。
3. 用相同的数据量，在可接受的重试范围内，把同一五分钟内的多次小提交合并为较大的批次，比较每批新增文件数、导入时延和失败重试成本。若仍需安排 Compact，给新旧文件共存留出余量，再跨过保留期看目录项净增长和删除记录。长期回收效果有待回访。
