# 广播发送等待与慢 Nested Loop

**测试已验证**

旧计划广播较大输入，接收端做 Nested Loop，发送端等待确认。调整连接键类型和半连接写法后，对照计划出现 Hash Semi Join，全量运行收益仍待验证。

从同一个查询的发送端和接收端一起看。接收端重复遍历较大输入时，发送端也可能因为下游消费慢而等待。单个等待发送的样本不足以指认网络故障。

比较连接键的类型、隐式转换、统计行数以及内侧输入被重复访问的次数。在同一日的数据上测试新旧写法，核对重复键和空值，检查各执行节点的行数、耗时及落盘。计划代价的下降不能直接折算成查询加速比。
